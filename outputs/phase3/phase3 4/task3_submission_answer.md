# Written Submission Answer - Task 3

For Phase 3 Task 3, I implemented an infrastructure-level performance profiling and bottleneck-elimination workflow covering database access, connection lifecycle, warm starts, caching and bounded concurrency. Because no PlaceMux production infrastructure or telemetry export was supplied, the implementation uses the real UCI Online Retail transaction dataset already established in the project as an external real-data proxy. The source is not presented as PlaceMux production telemetry.

The baseline configuration represents an intentionally inefficient path: a new database connection is created per request, no cache is used, and no warm-start priming is performed. The optimized configuration introduces a bounded SQLite connection pool, WAL/NORMAL database settings, warm-start initialization and a short-TTL cache for repeat summary and revenue reads. Load is generated concurrently so latency can be compared under the same workload conditions.

The script records p50, p95, average and maximum request latency, successful and failed requests, and produces before/after evidence in machine-readable form. It also captures the source-data scale used for the rehearsal, including raw rows, cleaned transaction rows, identified customers and retained revenue.

A deliberate failure-path test is included by reducing the connection pool to one connection and oversubscribing it with concurrent requests. The expected degradation is controlled 503 responses caused by pool exhaustion rather than an unbounded hang. This confirms that the infrastructure layer has an explicit failure mode and an operational signal for capacity tuning.

The implementation is fully code-driven and rollbackable by configuration. It documents the blast radius, runbook, performance signals, capacity controls and rollback path. The generated dashboard presents the before/after p95 latency, error behavior, infrastructure changes and failure-path result. All benchmark results are generated by `phase3/task3_infrastructure_demo.py` when executed against the real source on the user's machine.
